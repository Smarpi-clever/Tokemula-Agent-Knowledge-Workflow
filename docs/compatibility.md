CLI 隔离验证中，查询受限时先保留 pending，再由模型通过正式审批复用原回执补证。直接入口的旧复合 shell 样例缺少对应测试退出归属，继续保留为反例。

Desktop 日常验证保留 workspace-write 与 on-request。知识和状态位于该会话默认可写目录之外；首次 prepare 遇只读错误后，模型在同一普通任务内自行申请正式权限并重试，随后提交成功。第二个普通任务主动沿用正式权限流程。每轮实际各有 prepare、submit 两条 require_escalated 请求，共4条；此计数为工具权限请求数。授权作用域为对应合成映射的知识／状态写入及只读原生补证，原测试回执复用，原有全局策略保持。

App 的同名 projectless 新会话实际生成带后缀的独立目录。召回模型先得到该空映射的空结果，再自行显式选择原项目映射并读取对应笔记及测试来源；记录保留了实际目录与原映射的区别。

执行补证使用受支持的原生接口；接口不可用、分页达到上限或身份不匹配时，候选保留具体证据缺口。测试识别涵盖 `pnpm exec vitest run ...` 及简单 shell 包装。

真实历史修复保存精确报告入口和已核验的 Vitest 子范围：首次44项中43通过、1失败（exit1），后续单文件33项通过（exit0）。原82项汇总、lint、typecheck、build和12个浏览器场景的剩余证据继续 pending。启用映射 pending 从18变为17；停用旧验收映射另1项保持，总计18项。原任务、首次补证时间、人工正文与事实历史保留，重复拆分实测无新增写入或查询。

旧版 `prepare` 的只读数据库错误来自当前会话的文件系统写入作用域：引擎使用普通 SQLite 打开模式，所选知识与状态目录具备用户写位。真实升级与限定历史写入通过正式工具审批执行，保留原有沙箱和审批策略。

### 执行回执与事实核验

宿主提供结构化整数退出码时，测试与执行候选可使用对应任务的可信回执核验。本机 CLI 实测中，部分 `PostToolUse` 回执缺少此字段；这些测试候选保留为 pending，文件行为事实按匹配的文件证据独立核验。原生启用验证继续核对 Hook 信任、当前安装包与真实任务上下文。

## 安装条件

Python 3.11+、Git 和 Codex Desktop 为基础环境。Codex CLI 用于原生状态验证。Obsidian 可选；普通 Markdown 知识库可直接使用。GitHub 自动推送还需要已登录的 GitHub CLI 和已存在的私有知识仓库。

“一次启动向导完成设置”适用于依赖已经满足的环境。缺少依赖时，向导提供官方安装方式并保留设置进度；Hook 信任和三项自动化权限仍由用户确认。

## 原生插件布局

CLI 安装包保留 canonical 根 `plugin.json`。当前已验证的原生插件包由同一份元数据派生，使用单独的 `.codex-plugin/plugin.json` 布局。

当时测试的三个 runtime 对 legacy-only 插件发现了五个 Hooks；portable-only 与双 manifest 布局未加载这些 Hooks。因此发布包继续保留这条兼容路径。客户端或布局变化后，需重新验证实际发现、原生信任和普通任务触发。

插件入口通过手动 marketplace 安装。Setup 开关管理设置技能，自动维护的停止与恢复使用原生 Hooks 管理或 `akf` 命令。

官方说明：[Hooks 信任](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)、[插件与支持入口](https://learn.chatgpt.com/docs/plugins)。具体安装步骤见[安装与使用](install.md)。
